# 0014 — Local per-catalog policy decides whether catalog sysexts may be unsigned

- **Status:** Accepted
- **Date:** 2026-10-21

## Context

A catalog publishes each sysext's `<name>.conf`, a systemd-sysupdate
transfer whose `[Transfer] Verify=` controls whether `SHA256SUMS` must carry
a detached GPG signature (`SHA256SUMS.gpg`). Before #394, `RenderTransfer`
copied that value into the generated `.transfer`, so remote metadata could
switch signature verification off (#317). #394 fixed this by always
dropping the catalog's `Verify=`, which left every catalog transfer at the
systemd-sysupdate default, `Verify=yes`.

The Fedora and community fedora-sysexts catalogs publish `SHA256SUMS` over
HTTPS without a signature and declare `Verify=false`, so v2.0.1 broke them
(#439) and left administrators no supported override: the CLI `--verify` flag
only forces verification, and a hand-edited generated transfer is
overwritten by the next `catalog add`.

The constraints from #439: signatures stay required by default; only an
explicit local administrator decision, scoped to one catalog, may relax that;
remote metadata must not be able to grant that permission to itself;
`--verify` stays authoritative; a missing or invalid signature never causes an
automatic retry without verification; HTTPS, redirect-downgrade refusal, and
SHA256 checks are unaffected.

## Decision

The `.catalog` file gains `AllowUnsigned` (bool, default `no`). It is a
permission, not an override: it lets the catalog's own `Verify=` decide.

- **Render.** `RenderTransferTo` still drops every line the catalog conf
  spells as `Verify`. When the repo sets `AllowUnsigned=yes`, it re-emits the
  catalog's value as a canonical `Verify=yes` or `Verify=no` after
  `Features=`. The value is parsed by gopkg.in/ini.v1 with `MustBool(true)`,
  the same rule `config` applies when loading the transfer, so an absent or
  non-boolean value becomes `yes` and no disguised spelling can make the
  rendered and loaded values disagree. Without the opt-in, nothing is
  emitted and the default applies.
- **Use.** `Client.verifyPolicy` (`updex/list.go`), called by
  `getAvailableVersions` for every check, update, and install, maps a
  transfer carrying the catalog ownership marker
  ([ADR-0003](0003-catalog-ownership-marker.md)) to its owning repo. On each
  call it loads only that repo's `.catalog`, from the first of the client's
  catalog config roots that holds it, so an unrelated broken file cannot
  revoke the opt-in. A signature is required unless that repo is currently
  configured with `AllowUnsigned=yes`, and then the transfer's `Verify=`
  decides, provided the transfer's `Source.Path` is still
  `<SiteURL>/<name>` for the repo's current `SiteURL`. `ClientConfig.Verify`
  forces verification before any of this. A missing repo or an owning file
  that fails to load requires a signature, and so does a transfer header
  that cannot be read. The owning file is found with `os.Lstat`, the way
  `LoadReposFrom` lists it, so a dangling higher-priority symlink fails to
  load rather than letting a lower root's opt-in apply.
- **Transport.** A `.catalog` that sets both `AllowUnsigned=yes` and
  `AllowInsecure=yes` fails to load: without a signature, HTTPS is the only
  origin authentication left.
- **Errors.** `manifest.Fetch` wraps `manifest.ErrSignatureNotFound` for a
  404 on `SHA256SUMS.gpg`. `getAvailableVersions` prefixes that error with
  the rule that required the signature (forced; repo not opted in, not
  configured, or failing to load; a source outside the current `SiteURL`,
  with a hint to re-run `catalog add`; the generated transfer's own `Verify=yes`
  with a hint to re-run `catalog add` if the catalog now declares
  `Verify=no`; or a non-catalog transfer's own setting, which says the
  publisher must provide `SHA256SUMS.gpg`). Only a repo that loads but is not
  opted in is pointed at `AllowUnsigned=yes` and the trust it gives up.

## Consequences

- Fedora and community catalogs work again after one local line per catalog.
  A catalog that does publish signatures stays verified under the opt-in,
  unless its own conf says `Verify=no`.
- Revoking `AllowUnsigned` takes effect on the next check or update without
  re-adding. A `Verify=no` hand-added to a generated transfer has no effect
  without the opt-in. Transfers generated by v2.0.0, which kept the catalog's
  `Verify=false`, now require a signature until their repo opts in, and
  also need a re-add if the repo's `SiteURL` has changed since, such as an
  `AllowInsecure` `http://` catalog that moved to HTTPS.
- Transfers generated by v2.0.1 or v2.0.2 carry no `Verify=` line, so they keep
  requiring a signature after the opt-in until `catalog add` regenerates
  them. The README documents this migration.
- With the opt-in and a catalog `Verify=no`, publisher authenticity rests on
  the HTTPS origin: SHA256 catches corruption and mismatches against the
  published manifest, but anyone able to replace both image and manifest at
  the origin can serve a different image. The README states this trade-off.
- Each `getAvailableVersions` call on a catalog transfer re-reads the owning
  repo's `.catalog` file. It is small, and in exchange a long-lived SDK
  client cannot act on a stale policy.
- The trust decision now depends on reading the ownership marker
  correctly. `GeneratedFileRepo` reads enough bytes to fit the header for
  the longest possible repo name (a filename stem, at most 255 bytes). A
  file that starts with the marker but names no parseable repo requires a
  signature rather than being treated as hand-written.
- The trust decision also depends on the ownership marker being present.
  Stripping the marker from a generated transfer turns it into a hand-written
  transfer whose `Verify=` is honored. Only someone who can already write to
  `/etc` can do that.

## Alternatives considered

- **Honor the opt-in only at render time.** Write `Verify=` once during
  `catalog add` and trust the file afterwards. Rejected because revoking the
  opt-in would need a re-add, and the file alone could not tell an opted-in
  render apart from a hand edit.
- **Opt-in forces `Verify=no`.** Simpler, but it would turn verification off
  even for catalogs that sign, which takes away more than the catalog itself
  asked for.
- **Verify when a signature exists, otherwise accept unsigned.** That is an
  automatic fallback after a missing signature, which #439 rules out: a
  network attacker could make the `.gpg` request fail and get the unsigned
  path.
- **Couple to `AllowInsecure`.** Rejected: that key permits cleartext
  transport, and HTTPS is the only origin authentication an unsigned
  catalog has left. The two are refused together for the same reason.
- **Cosign-verified container distribution.** The catalogs sign container
  layers, not the raw `.raw` artifacts updex consumes. Supporting them would
  need a separate distribution and verification path.
