# 0003 — Repo-scoped marker headers record catalog file ownership

- **Status:** Accepted
- **Date:** 2026-08-12

## Context

`updex catalog add` writes `.transfer`/`.feature` definition files into
`/etc/sysupdate.<component>.d/`, and `catalog remove` deletes them again —
as root. The same component directory can also hold hand-written
definitions, package-shipped ones, or files added from a *different*
catalog configured with the same `Component`. A name match alone cannot
distinguish these: `remove docker` must not delete an administrator's
hand-written `docker.feature`, and two catalogs sharing a component must
not clobber each other's files. Review of PR #137 established that
name-in-component was too weak a signal, and that even a bare "generated"
prefix does not separate repos from each other.

## Decision

Every file catalog add generates begins with a machine-readable ownership
header naming the generating repo:

    # Generated by updex catalog (repo: <name>); managed by 'updex catalog'

This header is the authoritative ownership record (`catalog.GeneratedMarker`
and `markerLine` in `catalog/catalog.go`). `GeneratedFileRepo` parses the
repo back out, reading at most the first 256 bytes of the file
(`maxMarkerLen`). Mutating operations act only on files marked with the
acting repo:

- `CatalogAdd` refuses to overwrite an existing definition that is unmarked
  or marked by a different repo (`updex/catalog.go`).
- `CatalogRemove` claims a sysext only when its `/etc` component-dir
  `.feature` marker names that repo, and refuses to delete a `.transfer` it
  does not own — checked *before* the destructive
  `DisableFeature{Now}` teardown runs.
- `CatalogList` reports `Installed`/`Enabled` only for files whose marker
  names the listing repo, and `featureOrigin` (`updex/features.go`) reports
  the marker's repo as a feature's provenance, taking precedence over any
  path-based inference.

## Consequences

- Catalog operations can never clobber hand-written or package-shipped
  definitions that share a name or component, and two repos sharing one
  `Component` are isolated from each other.
- Ownership is recorded in the file itself, so it survives copies and
  works under a `--definitions` override where path-based provenance
  fails.
- An administrator who hand-edits a generated file but keeps its header
  keeps it catalog-owned; conversely, stripping the header orphans the
  file from catalog management (remove will refuse and point at
  `updex features disable`). Both are deliberate: the header is the single
  source of truth.
- The 256-byte read bound keeps ownership checks O(1) regardless of file
  size, at the cost of requiring the header to be the first line.

## Alternatives considered

- **Track ownership in a separate state file/database:** drifts from
  reality when files are copied, restored from backup, or edited; the
  in-file header cannot desynchronize from the file it describes.
- **Name-in-component membership as the ownership signal:** rejected in
  review — deletes hand-written files that merely share a name.
- **A bare marker without the repo name:** rejected in review — two
  catalogs sharing a `Component` would pass each other's ownership checks.
