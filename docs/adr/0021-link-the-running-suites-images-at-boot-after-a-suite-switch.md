# 0021 — Link the running suite's images at boot after a suite switch

- **Status:** Accepted
- **Date:** 2026-11-14

## Context

A sysext transfer can select the Debian suite with the `%w` specifier: the
snosi transfers use `MatchPattern=docker_@v_%w_%a.raw.zst`, and `%w` is the
`VERSION_ID` of os-release (13 on trixie, 14 on forky). updex expands it at
load time from the running system's os-release (#511).

A suite switch is a `bootc switch` from a trixie image to a forky image. The
timer service runs `updex features update --no-refresh`, so ADR-0016 applies:
it links at most what the next boot can run, and it never refreshes.

That leaves a window:

1. Before the reboot, the timer still runs on trixie: `%w` is 13, so it
   keeps the link on the trixie image (`docker_…_13_….raw`).
2. On the first forky boot, systemd-sysext refuses that image, because its
   `extension-release` names the trixie `VERSION_ID`. The feature is missing.
3. The next timer run (up to 6 hours later) links the forky image, but
   without a refresh. The feature comes back only at the next boot.

So a host can run a whole boot (or several hours plus a reboot) without an
enabled feature, such as docker, after every suite switch.

## Decision

- **A suite-switch run.** `UpdateFeaturesOptions.SuiteSwitchOnly`
  (`updex features update --suite-switch`) selects the enabled, unmasked
  features that have an active transfer whose sysext link points to an image
  of another suite: the base name of the link target matches the transfer's
  any-suite pattern (`config.TargetSection.AnySuitePatterns`, `%w` as a
  wildcard) and not its current pattern (`sysext.LinkedOtherSuiteAt`).
  - The first selection is a fast path, read without the lock. With no such
    feature, the run does nothing: no lock, no download, no link, no
    refresh, and no last-run record (the timer's record stays).
  - Otherwise the run takes the lock, loads the domain again and selects
    again before it downloads anything, because another updex operation can
    have moved the links between both reads. An empty selection under the
    lock ends the run the same way: no download, no refresh, no record.
  - With such features, it runs the normal update for exactly those features,
    as a run that names them: the operation lock, the rollback holds, the
    minimum-image gate, the refresh gate (ADR-0016) and the activation
    sequence (ADR-0019) all apply. The last-run record (ADR-0020) records a
    named run.
  - A domain that cannot be loaded is not a fast-path exit: the run goes on to
    the locked path, which records the failure (class `config`) as every
    update does. Only refused options and a confirmed empty selection write
    no record.
  - **It changes only its own links, and fails closed.** The refresh changes
    every pending state of the host, so the run skips it when anything else
    is pending, or when it cannot tell:
    - a pending activation outside the run (a link whose merged version is
      not known to equal it): an update that waits for the next boot under
      ADR-0016, for example a newer image that the timer linked with
      `--no-refresh` earlier on this boot (`refresh skipped: <component> has
      an update that waits for the next boot; …`);
    - a pending deactivation outside the run (merged, no usable link): the
      refresh unmerges it unless another systemd-sysext directory provides
      the image, which updex cannot prove (`refresh skipped: <component> is
      merged but not linked; …`);
    - a transfer whose state cannot be read (`refresh skipped: cannot read
      the state of <component>; …`);
    - host definitions that do not load: the run may be scoped to 1
      component, but the refresh is host-wide, and without the host's
      definitions updex cannot list what else it changes (`refresh skipped:
      the host's sysext definitions cannot be read, so what a refresh changes
      is unknown; …`).

    Every message ends with `the suite switch takes effect at the next boot`.
    The run keeps its new links, reports `RefreshSkipped` and records
    `refresh: skipped`; it is not an error. At boot, systemd-sysext merged
    every compatible link, so an activation case needs a timer run on the
    same boot before the unit.
  - It takes no feature names and cannot be combined with `NoRefresh`. Under
    systemd, a busy lock is an error for this run (not a skip): there is no
    later run on this boot.
  - A transfer without `%w` in its target pattern has no any-suite pattern,
    so it is never selected. A host whose links all name its own suite
    behaves as before.
- **A boot-time unit.** The package ships
  `/usr/lib/systemd/system/updex-suite-switch.service`, generated by the same
  code as the other units (`updex.SuiteSwitchUnit`, `scripts/units.sh`), and
  does not enable it:
  - `Type=oneshot`, `ExecStart=/usr/bin/updex features update --suite-switch`,
    `TimeoutStartSec=2h`;
  - `Wants=`/`After=network-online.target`, `Before=updex-update.service`;
  - `DefaultDependencies=no` with the usual basic dependencies written out
    (`After=sysinit.target basic.target`, `Before=`/`Conflicts=shutdown.target`),
    so `multi-user.target` does not wait for the network or a download;
  - `[Install] WantedBy=multi-user.target`;
  - no `ConditionACPower=`: a missing feature matters on battery too;
  - only the sandbox lines that need no mount namespace
    (`systemd.RefreshSandboxDirectives`): systemd-sysext mounts where the
    service runs, so `ProtectSystem=`, `ProtectHome=` and `PrivateTmp=` would
    hide the merged images from the host. The other dropped lines block what
    the refresh does (loop devices, module loads, the namespace of
    systemd-sysext itself, the `/etc` writes of systemd-sysusers and
    systemd-tmpfiles).
- `updex daemon enable` enables it with the timer (it writes it to
  `/etc/systemd/system` with the marker when no package ships the units), and
  `updex daemon disable` disables it (and removes it only when updex wrote
  it). `updex daemon status` reports it.

ADR-0016 stays: the timer still links for the next boot and never refreshes.
Only the boot-time unit refreshes, and only on the boot that needs it.

## Consequences

- On the first boot after a suite switch, the feature comes back on that boot,
  after the network is up and the new suite's image is downloaded (or at once
  when it is still staged, for a switch back).
- When the new suite has no image published yet, the run fails, the unit is
  marked failed, and the feature stays missing until an image is published
  and a later boot or a manual run links it, as before.
- The run never activates an update that ADR-0016 holds for the next boot.
  In the rare case that one is pending (the timer ran first on this boot),
  the suite switch also waits for the next boot, as the timer would have made
  it.
- snosi must enable the new unit with a preset line
  (`enable updex-suite-switch.service`), as it does for the timer; until
  then, only `updex daemon enable` enables it.
- One more packaged unit file, with its contract test, its CI
  `systemd-analyze verify` and its `.deb` check.
- The unit runs at every boot. On a boot without a suite switch it reads the
  domain and the links and exits; it takes no lock and writes nothing.

## Alternatives considered

- **Expand `%w` from the staged deployment's os-release before the reboot:**
  the timer would link the forky image while trixie still runs. That is
  specific to the bootc backend (other image backends have no staged
  os-release), and the running trixie system would refuse the linked forky
  image, so any refresh before the reboot (an `enable --now`, a manual
  update) would drop the feature on the old suite instead.
- **Refresh from the timer:** reverses ADR-0016; a live refresh every 6 hours
  restarts services of every feature that updated.
- **Keep both suites linked:** systemd-sysext has 1 link name per image, so a
  host cannot link 2 images of 1 component.
