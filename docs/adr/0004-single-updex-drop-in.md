# 0004 — 00-updex.conf is the only feature drop-in updex owns

- **Status:** Accepted
- **Date:** 2026-08-12

## Context

Feature enable/disable state is persisted through sysupdate-style drop-in
directories: `<feature>.feature.d/*.conf` files applied in alphabetical
order, each able to override any `[Feature]` key. Administrators use the
same directories for their own overrides (e.g. `50-local.conf`). updex
needs a deterministic place to write its enabled state without ever
competing with, overwriting, or deleting administrator configuration — and
teardown (`catalog remove`) needs to know exactly which files it may
delete.

## Decision

updex writes exactly one drop-in file per feature, named `00-updex.conf`
(`updexDropInName` in `updex/features.go`). Enable and disable both funnel
through `writeFeatureDropIn`, which writes only that file, into the
component scope the feature was discovered under. The `00-` prefix sorts
first, so with alphabetical application (`applyFeatureDropIns`,
`config/feature.go`) any administrator drop-in with a higher name always
overrides updex's state.

Everything else in a `.feature.d` directory belongs to the administrator
and is never touched: `CatalogRemove` deletes only `00-updex.conf` from the
drop-in directory, then removes the directory itself only via a plain
`os.Remove`, which refuses non-empty directories — so administrator files
keep the directory alive through a full catalog teardown.

## Consequences

- Enable/disable is idempotent and self-contained: rewriting one known
  file, never merging with or parsing administrator files.
- Administrators can permanently pin a feature's state with any
  `>00-`-named drop-in, and it survives every updex operation including
  catalog removal.
- updex cannot express more than one override per feature; any future
  setting updex wants to manage must share `00-updex.conf`.
- Because `00-` sorts first, updex's state is the *weakest* override. A
  user who expects `updex features enable` to win over a stale local
  drop-in must remove that drop-in themselves; updex chooses to lose that
  conflict by design.

## Alternatives considered

- **Editing the `.feature` file in place:** the base file may be shipped
  read-only in `/usr/lib` (or generated by catalog add and owned by that
  flow); drop-ins are the sysupdate-native override mechanism.
- **A high-priority name (e.g. `99-updex.conf`):** would let updex
  override administrator drop-ins, inverting the "local configuration
  wins" convention systemd directories follow.
- **Deleting the whole `.feature.d` directory on teardown:** destroys
  administrator files; deleting only the owned file and letting
  `os.Remove` no-op on non-empty directories preserves them structurally.
